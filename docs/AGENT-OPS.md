# Markii — Agent Ops Add-On

A chat-driven operations assistant that runs the merchant's store: inventory, catalog, pricing,
storefront changes, and routine analysis. Sold as a paid add-on.

> **Build order: last.** Explicit owner instruction, and technically correct — every tool this
> agent uses is an action from the registry, over APIs that must exist and be stable first. See
> `docs/PLAN.md` §7, Phase F.
>
> **What is *not* deferred:** the agent-native architecture itself — the shared action registry and
> MCP server — ships in Phase D with the builder (`docs/API.md` §22). This add-on is the *chat
> product* and its packaging, not the capability layer. By the time it starts, the tools already
> exist and have been exercised through MCP.

Not to be confused with two adjacent things: the **Agent Test Lab** (`docs/API.md` §12) simulates
*buyer* agents shopping the store; **agent-readable storefronts** serve third-party AI shoppers.
This is a *merchant-side operator* working for the store owner.

## 1. What it does

A chat window in the dashboard where a merchant can say:

- *"Mark everything in the Summer collection 20% off through Sunday"*
- *"We got 40 more of the navy hoodie in size L"*
- *"The homepage hero is too cramped on mobile — fix the spacing"*
- *"Which products are losing agent recommendations, and why?"*
- *"Write agent-facing descriptions for the 12 products missing one"*

Capability areas: catalog editing, inventory adjustments, pricing and discounts, collection
curation, storefront/CMS edits, catalog health remediation, channel configuration, and read-only
analysis and reporting.

**Never in scope for the agent:** billing and plan changes, payout or bank details, staff/role
management, data deletion beyond a single reversible item, publishing to a live storefront without
approval, and anything involving customer PII export.

## 2. Architecture

```
Chat UI (dashboard island)
   ↓ streaming
/api/agent/chat  — session, context assembly, model call, tool loop
   ↓
Action registry (docs/API.md §22) — the SAME actions the dashboard UI dispatches
   ↓  dry-run
Proposal — the diff the action would produce
   ↓
Approval gate — merchant approves → invoke → audit log → undo token
```

- **Tools *are* actions.** Not wrappers around them, not a parallel implementation — the agent
  calls the same `defineAction` entries the editor and the REST API call, with the same zod
  validation, the same server-side permission checks, and the same audit trail. There is no
  privileged agent path and no second copy of business rules to drift.
- **Proposals come from `dry-run`**, not from a bespoke proposal engine. The diff a merchant
  approves is exactly what the invocation will write.
- **Model access** via the AI SDK through Vercel AI Gateway using `"provider/model"` strings, so
  the model is configuration rather than a code dependency. Route long-running or multi-step jobs
  through a durable workflow rather than a single request.
- **Context assembly** is retrieval, not a dump: current store, recent orders/issues summary,
  relevant catalog slice, open readiness issues, and the current editor state when relevant. Cache
  aggressively; never put customer PII or secrets in the prompt.

## 3. Safety model

This agent has write access to a live business. The controls are the product.

**Propose → approve → execute.** Every mutation produces a structured diff (before/after per field,
affected item count, estimated impact) that the merchant approves before anything is written —
generated by `POST /api/actions/:id/dry-run`, reusing the Automations approval flow specced in
`docs/API.md` §15. Risk tier lives on the action definition, so the same policy applies whether the
call arrives from chat, an MCP client, or CI.

**Risk tiers**, merchant-configurable per store:

| Tier | Examples | Default |
|---|---|---|
| Read-only | Analysis, reports, drafts | Runs immediately |
| Low risk | Draft content, unpublished page edits, tags, internal notes | Auto-allowed (opt-out) |
| Medium risk | Inventory counts, product fields, collection membership | Approval required |
| High risk | Price changes, discounts, publishing, channel config, bulk edits over N items | Approval required, cannot be auto-allowed |
| Forbidden | Billing, payouts, staff, PII export, mass deletion | Blocked entirely |

**Hard requirements.** Bulk operations always preview the full affected list with a count before
execution and are capped per action. Every tool call is recorded in the audit log with actor
(`agent`), session, inputs, result, and timestamp. Every executed mutation carries an undo token
backed by CMS versioning or a field-level snapshot, with a stated undo window. Rate and spend caps
per session and per billing period, with graceful degradation at the ceiling. The agent must state
uncertainty rather than guess at destructive intent — an ambiguous instruction gets a clarifying
question, not a best guess. And the chat surface never claims an action succeeded until the tool
result confirms it: no optimistic success messages.

**Prompt injection is a live threat here.** This agent reads merchant-controlled *and*
third-party-influenced content — product descriptions from imports, scraped catalogs, customer
notes, form submissions. Treat all of it as untrusted data, never as instructions: mark retrieved
content as data in the prompt, keep tool authorization independent of anything the model read, and
require approval for high-risk actions regardless of how confidently the model proposes them.

## 4. API surface (PLANNED)

```
POST   /api/agent/chat              — stream a turn; SSE over the default Node runtime
GET    /api/agent/sessions          — list sessions
GET    /api/agent/sessions/:id      — transcript + tool calls + proposals
POST   /api/agent/proposals/:id/approve
POST   /api/agent/proposals/:id/reject
POST   /api/agent/executions/:id/undo
GET    /api/agent/audit             — filterable tool-call log
GET    /api/agent/usage             — actions and spend this period, against entitlement
PUT    /api/agent/settings          — risk-tier policy, allowed capability areas, caps
```

```ts
interface AgentProposal {
  id: string;
  sessionId: string;
  capability: "catalog" | "inventory" | "pricing" | "cms" | "channels" | "health";
  riskTier: "read" | "low" | "medium" | "high";
  summary: string;                 // one line, merchant-readable
  rationale: string;               // why, grounded in store data
  diffs: { entity: string; entityId: string; field: string;
           before: unknown; after: unknown }[];
  affectedCount: number;
  status: "pending" | "approved" | "rejected" | "executed" | "failed" | "undone";
  undoToken: string | null;
  createdAt: string;
}
```

## 5. Chat UI

Dockable right-side panel available across the dashboard, carrying page context (viewing a product
→ that product is in scope). Streaming responses, cancel mid-turn.

Proposals render as **inline diff cards** with Approve / Reject / Edit, showing affected items and
counts — not a wall of prose the merchant has to trust. Executed actions render as receipts with an
Undo button and a link to the audit entry. Failed tool calls show the real error, never a softened
paraphrase. Sessions are named, searchable, and resumable.

Suggested prompts appear only when grounded in real store state ("You have 12 products missing
descriptions — want me to draft them?"), never as generic filler.

## 6. Pricing & metering

Add-on subscription plus a monthly action allowance; overage metered or capped by merchant choice
(see `docs/PRICING.md` §2). Bill on **executed actions and token spend**, not on messages sent —
merchants shouldn't pay to ask a question. Read-only analysis should be cheap or free to encourage
the habit. Usage is visible live in the panel and on the billing page, and the agent warns before
an action would exceed the allowance.

## 7. Build order

Prerequisite from Phase D: the action registry, MCP server, `dry-run`, undo, and audit log already
exist. This phase adds the conversational layer on top.

1. Chat shell, session persistence, streaming, context assembly (read-only Q&A first — genuinely
   useful and carries near-zero risk)
2. Bind read-only actions as tools: catalog search, analytics summaries, health issue explanation
3. Proposal rendering in chat (diff cards) over the existing `dry-run` + approval gate
4. Low/medium-risk write actions: content drafts, inventory, product fields
5. Risk-tier policy settings UI; surface the existing undo path in chat receipts
6. High-risk actions: pricing, discounts, publishing, bulk operations
7. CMS editing actions (already defined in Phase D — this is exposure, not new capability)
8. Metering, entitlements, caps

Shipping step 1–2 alone is a real product. Resist bundling write access into the first release.

## 8. Open decisions

- Does the agent edit CMS page trees directly, or only propose diffs? (Recommendation: diffs, same
  as everything else)
- Scheduled/proactive agent runs ("watch inventory nightly") — v2 of the add-on, needs its own
  consent model since it acts without a merchant present
- Is there a fully autonomous mode for merchants who want it, and what does it require them to
  accept?
- Does the agent get access to customer records at all? (Recommendation: aggregate only, no
  individual PII)
- Model selection and cost ceiling per tier
